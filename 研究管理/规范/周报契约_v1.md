# 周报记录与下周预期契约（v1）

本规范定义 `研究管理/周报记录/<week_id>.json`（规范源）与 `研究管理/派生/周报/`（派生视图）的结构、承接规则与下周任务可行性门禁。Python 3.12 标准库实现，不修改根目录历史周报或受保护输入。

## 1. 标识与目录职责

- `week_id`：采用 ISO 周标识 `YYYY-Www`（如 `2026-W47`），`period_start`（周一）与 `period_end`（周日）须与 `date.fromisocalendar(year, week, 1..7)` 严格一致；目标下周窗口自动计算为紧邻的下一 ISO 自然周。
- 规范源：`研究管理/周报记录/<week_id>.json`（`schema_version = "weekly-record.v1"`）。
- 默认自包含交付文件夹（主形态）：`周报/<week_id>_<author>/`（由 `.reports.lock` 串行化发布，仅校验已登记 `week_id` 对应目录；`周报/` 下允许并存只读历史归档如 `2026-W45_<author>/`、`2026-W46_<author>/`）：
  - 主周报：`周报_<week_id>_<author>.md`（文内“数据或文稿链接”指向包内 `相关材料/` 相对路径，零 `../../../` 外链，带生成标记禁止覆盖手工文件）。
  - 导师英文进展稿（可选）：`导师进展邮件_<week_id>_en.md`。
  - 目录与来源说明：`目录与来源说明.md`（100% 确定性生成，**严禁写入壁钟时间 `now()`**，仅引用 `period_start` / `period_end` / `as_of_date`，列出包内全部文件、用途、工作区规范源路径、字节数与 64 位 SHA-256）。
  - 相关材料目录：`相关材料/`，逐字节复制 `tracks[].deliverable_refs[]` 与可选顶层 `extra_bundle_refs[]`（按规范源路径去重；支持可选 `bundle_name` 单层安全文件名校验与 `purpose` 说明；支持可选 `bundle_notes` 边界说明）。`check` 与 `refresh` 均校验副本字节一致且拒绝存在未登记的孤立文件或符号链接（不静默删除未知文件）。
- 单文件兼容镜像（向后保留）：`研究管理/派生/周报/` 下同步生成 `周报_<week_id>_<author>.md` 与 `导师进展邮件_<week_id>_en.md`（沿用历史六要素项目版式与工作区相对链接，带生成标记与 `.reports.lock` 保护，非生成文件拒绝覆盖）。
- 历史归档打包视图：`周报/2026-W45_<author>/` 与 `周报/2026-W46_<author>/` 为只读归档文件夹，工作区根目录原 `周报_W45_*`、`周报_W46_*` 及附件原件保持原位（其中早期历史审阅稿可由 `2026-W47.json` 的 `parent_ref` 锁定）。

## 2. 上周承接契约（防断档、防篡改）

1. **父周引用（`parent_ref`）**：
   - 首周允许 `parent_ref = null` 且 `is_initial_week = true`；其余周必须提供 `parent_ref`，并通过 `verify_ref` 校验文件存在、字节数与完整 SHA-256。
   - `parent_ref.kind = "legacy_markdown"`：只读解析既有历史审阅稿 Markdown 中各项目小节的 `- 下周计划：` 条目（按分号切分独立子项）及 `## 需要决定或协助`。
   - `parent_ref.kind = "weekly_record"`：只读读取上一周 `weekly-record.v1`（须为上一连续自然周或显式说明合周范围）中各项目的结构化 `next_week_plan` 列表。
2. **上周计划原文锁定**：本周派生的 `- 上周计划：` 完全由 `parent_ref` 自动回填，禁止在当前周 JSON 中手写覆盖上周承诺。
3. **逐项对账（`carryover_reconciliation`）**：
   - 上周每个项目的每一条 `next_week_plan` 子项，本周必须按 `parent_item_id` 唯一对账，不允许遗漏或重复。
   - `outcome` 枚举：`done`、`partial`、`deferred`、`blocked`、`dropped`。
   - **未完结项闭环约束**：凡 `outcome` 为 `partial`、`deferred` 或 `blocked` 的条目，必须满足二者之一：① `continued_by_task_id` 指向本周某条有效 `next_week_plan` 任务；② `deferred_to_backlog_id` 指向本周 `deferred_backlog` 中的暂缓条目（写明原因与重开条件）。静默丢弃未完结任务直接判定校验失败。

## 3. 下周任务合理预期门禁（防跨门禁跳步、防超载、防口号）

每条 `next_week_plan` 任务包含：`task_id`、`summary`、`kind`、`effort`、`commitment`、`dependency`、`due_date`、`deliverable_or_criterion`、`if_blocked_fallback`。

1. **日期窗口门禁**：`due_date` 必须为合法 `YYYY-MM-DD`，且落在目标下周 `[next_week_start, next_week_end]` 闭区间内。
2. **科研阶段与决定依赖门禁**：
   - `kind` 枚举：`advisor_alignment`、`literature_check`、`data_audit`、`scenario_abstraction`、`dev_exploration`、`system_engineering`、`formal_experiment`、`result_analysis`。
   - 当项目绑定了 `problem_id`（对应 `研究管理/问题/<problem_id>/`）时，工具实时读取该题卷宗、`决策.json` 与 `design.json`：
     - 若 `formal_use_allowed` 为 `false` 或存在未确认的必需科研决定，严禁将 `formal_experiment` 或 `result_analysis` 列入 `next_week_plan`；
     - 若核心题面参数（`target_offtarget`、`endpoint`、`source_selection`）仍为 `null`，则 `dev_exploration` 任务不得标为无条件承诺（`commitment = "committed"` 且 `dependency = "self_contained"`），必须设为 `commitment = "conditional"` 且写明依赖与回退动作，或放入 `deferred_backlog`。
3. **单周容量预算门禁（`capacity_budget`）**：
   - 工作量点数：`S = 1`（≤2 小时）、`M = 2`（半天至 1 天）、`L = 3`（2–3 天）。
   - 默认单周上限（可在记录中收紧，不得放宽超过硬上限）：
     - 确定承诺任务（`commitment = "committed"`）总数 `<= 3`（硬上限 `4`）；
     - 确定承诺任务工作量总点数 `<= 6`（硬上限 `8`）；
     - 大体量任务（`effort = "L"`）总数 `<= 1`；
     - 条件触发任务（`commitment = "conditional"`）总数 `<= 2`。
   - 超出单周容量的候选事项必须移入 `deferred_backlog`（渲染于周报末尾“暂缓与后续池”），不在下周计划中堆砌不可达目标。
4. **可核验交付物与外部阻塞兜底门禁**：
   - 每条任务必须提供非空的 `deliverable_or_criterion`（明确产出文件或判停标准，拒绝无判据抽象表述）。
   - 凡 `dependency` 为 `awaits_pi` 或 `awaits_external` 的任务：若 `commitment = "committed"`，必须提供非空 `if_blocked_fallback`（若外部反馈未按期到位时可独立推进的零悔动作）；若无独立兜底动作，必须标为 `commitment = "conditional"`。

## 4. 系统事实后台核对（S01 / S17 / 状态一致性，不污染周报正文）

生成与检查周报时，工具在后台读取工作区事实并通过 CLI JSON（`capacity_usage`、`run_diagnostics`）返回诊断，**不在派生的周报 Markdown 正文中插入机器核对面板**：
- 校验课题已确认决定数与项目描述一致性（若决定数为 `0` 且无研究运行，禁止声称“已完成正式实验”）。
- 按各周 `as_of_date` 时间截断读取 `实验登记/` 事务日志：统计已提交探索性/确认性运行数（排除 `smoke` 与 `local_fixture`），在 CLI JSON 的 `running_alerts` 中返回仍停留在 `running` 的运行（S01），并在 `budget_overruns` 中返回按 `group_id` 汇总超出 `预算.csv` 上限的组（S17）。
- 校验本周引用的全部本地文件引用（`evidence_refs`、`deliverable_refs`、`extra_bundle_refs`）真实存在且 SHA-256 匹配。

## 5. 人读行文与叙事逻辑规则（前台 Markdown 强制约束）

周报是面向导师与研究者的正式沟通文档，不是机器日志或流水账清单。规范源与渲染器共同强制执行以下五条规则：

1. **前后台语汇隔离（零机器符号、零工程黑话）**：
   - 任务编号（`W49-T1`）、暂缓编号（`BL-xxx`）、工作量档位（`S/M/L`）、依赖枚举、竖线拼接符（`｜`）与状态方括号（`〔已完成〕`）仅用于 JSON 后台核验，**严禁出现在派生的周报正文中**。
   - 周报正文须使用研究与领域自然语言，**禁止直接罗列内部脚本名、数据库实现细节或门禁代号**（如 `verify_project.py`、`make_report.py`、`check_all.py`、`runs.jsonl`、`freeze.json`、`决策.json`、`design.json`、`SQLite`、`FTS5`、`G1`/`G2`/`G3`、`Gate-3A`、`W10b`、`PASS/FAIL` 计数等）。
2. **`完成情况` 须写清因果链，禁止机械拼接**：
   - 凡存在上周承接项的核心研究项目，必须填写连贯的 `completion_summary`，在一句话内交代“哪部分已完成、哪部分未完结、以及未一步到位的真实研究原因（如数据审计暴露样本限制或外部讨论顺延）”，不得仅把各子项备注用分号硬拼。
3. **`本周进展` 须按“问题 → 核查与证据 → 方案推论”分层递进，禁止单纯罗列动作**：
   - 绑定了 `problem_id` 的核心课题项目，除一句总起说明本周聚焦解决的矛盾外，必须提供 `progress_points`（`2–4` 个有逻辑承接关系的要点，典型结构：① 做了什么数据/文献/实验核查与具体量化依据 → ② 发现了什么关键瓶颈或边界 → ③ 据此对课题方案或下一步作出的推论），拒绝无主线的零散事务罗列。
   - 非主线背景维护项保持一段简明说明即可，不凑字数。
4. **`下周计划` 须呈先后依赖链条，自然内化条件与兜底**：
   - 日期统一渲染为自然中文（如 `12 月 2 日前`）；存在多项任务时按先后依赖排为 `1 → 2 → 3`（如：先完成定量摸底产出对照表 → 再据此与老师确认选题与端点 → 待确认后启动开发集基线摸底）。
   - 条件触发项在日期后自然注明前提（如 `12 月 6 日前（待与老师确认目标体系与端点后启动）：……`）；外部依赖项的顺延兜底直接以括号融入句末，不单列字段标签。
5. **`暂缓事项` 讲清取舍依据**：每条以自然句式写明“暂缓什么：为何当前不占用下周精力；待什么条件出现时再安排”，不暴露内部编号。
